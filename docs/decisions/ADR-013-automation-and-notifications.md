# ADR-013: Automation and notifications

**Status:** Accepted (Phase 6). Implements `docs/architecture.md` §3.4 and §3.5, and pulls the core of the audit log forward from Phase 10.

## Context

When something happens in NEXUS (an incident opens, a service goes down, a deployment fails) people want to be told, other systems want to be called, and sometimes an incident should be opened automatically. This must not become a scatter of hard-coded triggers inside incident, monitoring and deployment code. It must stay correct with several workers, retries and restarts; it must never cross a tenant boundary; it must not be able to run away (loops, floods); and administrators must be able to see who changed it.

## Decisions

1. **A transactional outbox.** Whatever changes something automation may care about writes a `DomainEvent` in the **same transaction** as the change. A rolled-back change leaves no event; a committed change can never lose its event because a process died before enqueueing. Each source has exactly one chokepoint: `recordIncidentEvent` (the single writer of incident timeline events, which the API's own writer now delegates to), `recomputeServiceHealth` (announces real health changes) and the worker's deployment upsert (announces a deployment reaching SUCCESS or FAILURE).
2. **The database is the scheduler, again (ADR-011).** A dispatcher in the worker claims undispatched events with `FOR UPDATE SKIP LOCKED`, decides which rules match, and records one `AutomationExecution` per match, all in **one transaction** that also marks the event dispatched. A crash before commit leaves the events untouched; a crash after leaves executions that a sweep enqueues. `(rule, event)` is unique and the queue job id is deterministic, so nothing runs twice however many workers exist.
3. **Rules are data, validated in one place.** The trigger catalogue, the facts each trigger carries, the condition operators, the action schemas and the template language live in `packages/shared`; the API validates with them, the worker evaluates with them and the UI builds its forms from them, so they cannot disagree. Conditions and templates can only see flat scalar _facts_, never raw records. Templates are plain `{{fact}}` substitution: no expressions, no HTML, values length-limited and stripped of control characters, single-line output for titles and email subjects. Rule templates offered in the UI are ordinary rules, not special code.
4. **A typed allow-list of actions:** `notify`, `webhook`, `create_incident`. Adding one means a schema in `shared` and a handler in the worker. `create_github_issue` is deliberately **not** in Phase 6: it needs a stored GitHub credential, which is a separate integration to design properly (ADR-012 had deferred outbound GitHub calls to "where a credential is actually needed"; that is still later).
5. **Safe to run twice.** Each action's result is saved as soon as it is known, so a retry resumes: it skips what finished and only repeats failures that could pass on a second try (a timeout, a 5xx), never permanent ones (a bad address, a 404). A `Notification` row is the per-recipient delivery record and is unique per `(execution, action, recipient)`, holding whether an email went out, so a retry never duplicates a notification or an email. `create_incident` stamps its execution and action on the incident's CREATED event and checks for it under an advisory lock. A webhook's delivery id is constant across retries so receivers can deduplicate. A finished execution is never re-run.
6. **Safety valves.** A per-rule cooldown keyed by the subject (the incident, service or deployment), an hourly execution cap per rule, a limit of 50 rules per organization, 5 actions per rule and 200 recipients per notification. Skipped executions are **recorded** with the reason, not silently dropped. A rule disabled after its execution was queued stops before doing anything.
7. **No automation chains.** An event caused by an automation (`causedByExecutionId`) is marked dispatched without running any rule. An automation therefore cannot open an incident that triggers more automation, however the rules are written. The consequence is stated in the UI: a rule that opens an incident should also notify people itself.
8. **Tenant isolation is structural.** Every table carries `organizationId` with composite foreign keys. A notification's key points at `OrganizationMember`, so one can only exist for a member of its own organization. The executor reads the organization from the stored event, never from a job payload. Recipients and webhook destinations are validated when a rule is saved **and again when it runs**, because membership and destinations change.
9. **Notifications.** In-app notifications are the user's own inbox: every query is scoped by the user from the verified session, never a parameter. Email goes through a transport seam: `log` (default, no external service) or SMTP (nodemailer). Email is plain text only; recipient addresses always come from user records, never from rule input; failures are classified retryable or permanent; credentials never appear in an error. The bell polls until real-time updates (Phase 7).
10. **Outbound webhooks.** A destination is an organization-managed record with an encrypted signing secret (AES-256-GCM, bound to its id; shown once). Each call is one JSON POST signed `sha256=HMAC(secret, "<timestamp>.<body>")` with the timestamp in the signed text so a receiver can reject replays. They reuse the monitoring SSRF protections unchanged: validated on save and again at send time, DNS pinning, no redirects, body never read, hard deadline, with the same operator switch for private networks. The worker now needs `INTEGRATION_ENCRYPTION_KEY` to decrypt secrets in memory.
11. **An audit log, pulled forward from Phase 10.** Automation is security-sensitive configuration, so shipping it without a record of who changed it would be a step backwards. `AuditLog` is append-only, enforced by database triggers (UPDATE, DELETE and TRUNCATE are refused, and an organization cannot be deleted out from under it). Entries are written **inside the transaction** of the change they describe. Because they can never be edited, metadata is **redacted before writing**: keys that look like credentials, URL query strings and oversized values never reach it. Covered now: automation rules, outbound webhooks, GitHub integrations and incidents opened by automation. Broader coverage and the operator tooling remain Phase 10.
12. **Retention.** An hourly job deletes dispatched events (and their executions) and notifications past their windows (`AUTOMATION_RETENTION_DAYS`, `NOTIFICATION_RETENTION_DAYS`, 90 days by default). Undispatched events are never deleted: they are work still to do. The audit log is not subject to retention.

## Consequences

Rule evaluation adds one insert per automatable change and a short delay (the dispatcher polls, by default every second). Because automation cannot chain, some workflows need one rule with several actions rather than two rules. Email needs an SMTP server to leave the worker log. Not built, by design: `create_github_issue`, per-user notification preferences and digests, push updates, Slack or other channels (each is a new transport or action, not a redesign), and audit coverage of the rest of the product.
