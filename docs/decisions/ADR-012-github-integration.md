# ADR-012: GitHub integration

**Status:** Accepted (Phase 5). Refines the GitHub webhook flow in `docs/architecture.md` §3.2.

## Context

NEXUS should know what was deployed and when, so that an incident can be traced back to the change that probably caused it. GitHub reports deployments by sending webhooks to a public URL. That URL is reachable by anyone on the internet, so everything it receives is untrusted until proven otherwise, and the integration must stay correct when GitHub retries, redelivers or reorders events.

## Decisions

1. **Per-repository webhooks, not a GitHub App.** Each integration is one repository, one secret and one URL. It needs no app registration, OAuth flow or callback URL, so it also works for self-hosted installs. The cost is a manual setup step in GitHub. NEXUS only _receives_ data; calling the GitHub API (for example creating an issue) needs a stored credential and is not done yet; Phase 6 (ADR-013) deliberately leaves it out too.
2. **The webhook is authenticated by signature, not by session.** `POST /api/v1/webhooks/github/:integrationId` is public. The API verifies `X-Hub-Signature-256`, an HMAC-SHA256 of the **raw request bytes** (captured before JSON parsing, never re-serialised), against that integration's own secret, with a constant-time comparison. Because a request from GitHub carries no `Origin`, that one path prefix is exempt from the CSRF origin check; nothing else is. The web app's proxy forwards the three GitHub headers and the exact body, since in the Docker layout the API is not publicly reachable.
3. **Nothing unauthenticated is stored or acted on.** A bad or missing signature is answered with 401 and is not persisted. Repeated bad signatures from one address for one integration are throttled (10 per 15 minutes, then 429); all deliveries per address are limited to 300 per minute. Valid deliveries are never affected by the bad-signature counter, so an attacker cannot lock out GitHub.
4. **Secrets are shown once and encrypted at rest.** The secret is 256 random bits generated by the server and returned only in the creation response. It is stored AES-256-GCM encrypted with the row id as authenticated data, so a ciphertext copied onto another row does not decrypt. The key is `INTEGRATION_ENCRYPTION_KEY`; while it is unset, integrations are disabled with a clear 503 and the rest of NEXUS is unaffected. Rotating a secret means disconnecting and reconnecting the repository.
5. **Idempotent by construction.** A delivery is unique per `(integration, deliveryId)`. This is deliberately per integration rather than global (the original design had `(provider, deliveryId)`), so one tenant can never suppress another's delivery by reusing an id. A deployment is unique per `(integration, GitHub deployment id)`, so its successive statuses update one row. Each status carries its own timestamp and only a newer one changes the deployment, so out-of-order delivery is harmless. `deployedAt` is the first time it reported success and never moves.
6. **Acknowledge fast, process in a worker.** The API verifies, stores the delivery and enqueues a `webhook-processing` job (job id = the stored event id), then answers 202. If enqueueing fails the stored delivery is removed and the API answers 503, so GitHub's redelivery is processed instead of being dropped as a duplicate. The job carries only ids, never the payload.
7. **Only what NEXUS understands is stored.** `deployment_status` (and `ping`) are handled. Other event types are acknowledged and not stored. A `push` is not a deployment, so commit and pull-request normalisation is left out rather than guessed at. Permanent problems (malformed payload, unsupported state) mark the event `FAILED` without retrying; only transient errors are retried, and exhausted retries are recorded on the event.
8. **A valid signature is not proof of relevance.** The worker also checks that the event's repository matches the integration's, and refuses it otherwise.
9. **Disable, do not delete.** Removing an integration disables it: deliveries get 404, history and links stay, and a partial unique index (one _active_ integration per repository per organisation) frees the repository name.
10. **Deployments are linked to incidents by a human, with suggestions.** For an incident on a service, successful deployments to that service in the two hours before the incident began, and not yet linked, are suggested. Linking is explicit, records `SUSPECTED` or `CONFIRMED` and who did it, and writes a `DEPLOYMENT_LINKED` timeline event in the same transaction. Nothing is linked automatically (an automation action that links deployments could be added later; none exists yet).
11. **Raw deliveries are retention-limited.** They hold full payloads, so an hourly job deletes them after `WEBHOOK_RETENTION_DAYS` (30). The deployments they produced are kept.

## Consequences

Setup needs a manual step in GitHub and a URL GitHub can reach (a locally running NEXUS needs a tunnel). Commit messages are not available, because `deployment_status` does not carry them. There is no unlink yet. In exchange the endpoint has a small, well-tested attack surface: it does no work for an unauthenticated caller beyond one HMAC, stores nothing from one, and cannot be replayed into a duplicate or into another tenant.
