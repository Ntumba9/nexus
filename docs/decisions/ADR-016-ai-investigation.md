# ADR-016: AI investigation

**Status:** Accepted (Phase 9). Implements the pipeline in `docs/ai.md` and the isolation rules of ADR-006, on top of the retrieval of ADR-015.

## Context

During an incident an engineer wants a starting point: what changed, what is failing, has this happened before, which runbook applies. A language model can help, but the platform must stay honest and safe: the material it reads is partly written by attackers (comments, documents, commit messages, response bodies), its output is not to be believed just because it sounds sure, and the feature must cost nothing to run and must not depend on any one vendor or paid key.

## Decisions

1. **The provider is an interface, and the default is not a model.** `AnalysisProvider { id, label, kind, analyze(input) }`. Three settings: `rules` (default), `openai`, `none`.
   - `rules` is a deterministic rule engine over structured facts: a deployment shortly before the incident, health checks that keep failing (and their most common reason), earlier incidents on the same service, matching runbooks. It needs no key, no network and no download, it is labelled "Built-in rule-based analysis (no AI model)" everywhere it appears, and its confidence never exceeds medium.
   - `openai` calls any OpenAI-compatible `/chat/completions` endpoint, so a local Ollama or a free hosted tier (Groq, Google Gemini's OpenAI endpoint, OpenRouter) works by changing three variables. Anthropic is not wired in because it has no free tier; the interface is where it would go.
   - `none` switches the feature off: the button explains why, nothing is queued, history stays readable.
2. **Investigations run in the background, once.** The API only records a request and queues a job. A **partial unique index** allows one queued or running investigation per incident, so two clicks or two API instances cannot start two model calls; the loser gets 409. An investigation stuck for ten minutes (a worker died) is failed by the next request rather than blocking the incident. Each person may start ten per hour, and if the limiter is down the request is refused rather than left unmetered.
3. **Context is assembled, bounded, redacted and labelled.** For an incident the assembler reads, all scoped by the organization: its timeline (never its own earlier investigations), deployments to the service in the 24 hours before onset, recent health-check results, earlier incidents on the service, and runbooks found by ADR-015 retrieval. Each source gets a stable label (`INC-EVT-1`, `DEP-2`, `MON-3`, `INC-PREV-1`, `KB-1`), is cut to 1 500 characters, and the whole is held to 24 000 characters by dropping the least useful material first (never how the incident was opened). Credentials are removed before anything is stored or sent (bearer and basic tokens, common API-key formats, JWTs, private keys, `user:password@` in URLs, `password=` style assignments). If material is left out the answer says so.
4. **Sources carry structured facts, taken from records.** The rule engine reads `facts` (status, minutes before onset, failure reason…) that the assembler took from database columns, never text it parsed. A model is sent the text only.
5. **Untrusted content is data, and the answer is verified.** Sources are wrapped in `<source label=… kind=…>` blocks and the system prompt states that everything inside them is untrusted and must never be followed. Anything that could open or close a block (`<source`, `</source`, `<system`…) is neutralised in the text, the description and the question. Then the answer is treated as untrusted whoever wrote it:
   - it must parse against a strict schema (unknown shapes are rejected, not repaired);
   - **every citation is checked against the labels that were really provided.** An invented label is removed, an evidence statement left with no valid source is dropped, and a cause claimed as evidence with none is shown as inference. With no grounded evidence left, the overall confidence cannot be more than low.
     The UI shows the counts of what was removed. The worst a successful injection can do is produce a misleading summary that arrives flagged as ungrounded, because the model has no tools, nothing it writes is executed, and recommended actions are advisory text.
6. **The snapshot is the record.** The exact sources are stored next to the verified answer, so a citation opens what the analysis actually read even after the underlying records change. The stored answer is parsed again when it is read.
7. **Failure is quiet and safe.** A transient provider failure (timeout, 429, 5xx, an unusable reply) is retried by the queue (three attempts); a permanent one (401, 404) fails at once. The stored reason is short and comes from a fixed vocabulary: never a provider message, a URL, a key or the model's reply. A failed run adds nothing to the timeline. A successful run adds one `AI_INVESTIGATED` event, attributed to the person who asked.
8. **Permissions and tenancy.** Reading needs `incidents.read`; starting needs `incidents.update`. The investigation row references its incident through the composite tenant key, the worker reads the organization from the stored row (never the job payload), and a foreign incident id gives the same 404 as an unknown one. Starting is audited without the question text.
9. **Live.** A finished run announces the `ai` and `incidents` topics on the real-time stream (ADR-014); the page polls every 2.5 s only while one is running.

## Consequences

The feature works, honestly labelled, with no setup and no cost. A local or free-tier model adds real language understanding at the price of variable quality, which is why its output is verified rather than believed. Because the rule engine and a model share one schema and one verifier, switching is a configuration change. Not built, by design: streaming answers, chat follow-ups, model tool use, automatic investigation when an incident opens (an automation rule could trigger one later), vendor-specific SDKs, and per-organization model choice.
